# Room Engine v0.1 Complete Architecture Specification

> **For Hermes:** Use subagent-driven-development only after this architecture is explicitly approved. This document is a specification, not authorization to implement.

**Goal:** Two humans and their separately identified AI agents collaborate concurrently in one permissioned project room, exchange information without manual copying, update shared state safely, escalate decisions to humans, resume after approval, and produce a complete attributable history.

**Architecture:** A TypeScript modular monolith with separate web, API/realtime, and agent-worker processes. PostgreSQL stores normalized current state, immutable room events, command idempotency receipts, and durable jobs. Commands mutate state and append events atomically. Clients synchronize using snapshots plus per-room ordered event replay. Agents interact only through permission-checked Room Engine commands and provider-neutral model adapters.

**Tech Stack:** TypeScript, Node.js, Fastify, Next.js/React, PostgreSQL 16, Drizzle ORM, pg-boss, Zod, native WebSocket, Vitest, Playwright, Docker Compose. Production object storage, advanced authentication, and richer policy infrastructure are Phase 1B concerns.

## Approved amendments (2026-08-24)

### Phase 1A: prove the multiplayer room

Phase 1A contains only the shortest complete collaboration loop:

- company, user, agent, and separate principal identities;
- project room creation, membership, and manager/contributor/worker-agent permissions;
- organic room conversation and agent-addressed messages;
- task creation, assignment, and status updates;
- immutable room-ordered events;
- snapshot plus reconnectable realtime synchronization;
- agent runtime with deterministic fake provider and one OpenAI-compatible provider;
- human decision request, approval or redirect, and agent resume;
- normalized shared project briefing/context;
- minimal UI for two humans and two agents;
- concurrency, idempotency, reconnect, and room-isolation tests.

Phase 1A is not blocked on production S3, sophisticated artifact ACLs, full external-action execution, advanced OIDC, multiple production model providers, complex policy systems, or enterprise secret infrastructure beyond safe local/development handling.

### Phase 1B: hardening and expansion

Phase 1B adds production object storage and artifact ACLs, fuller external-action execution, advanced identity integration, additional provider adapters, richer policy/approval systems, and production secret-management hardening.

### Scheduler constraint, not domain invariant

One active run per agent/room is a v0.1 scheduler limit only. Data structures use independent `agent_run` identities and do not impose a permanent uniqueness constraint that would prevent one agent from executing multiple concurrent work items later.

### Conversation-first room

Conversation is a first-class room primitive. Messages do not require a task association. Tasks structure work but do not define every interaction or trigger.

Agent-addressed messages remain auditable by authorized managers/admins. Phase 1A contains no truly secret agent-to-agent threads inside a shared project room.

### Shared project briefing

Every room exposes a normalized briefing containing:

- project objective;
- current participants and roles;
- joining/resuming agent's role;
- assigned responsibilities;
- active tasks;
- relevant completed work;
- unresolved decisions and blockers;
- relevant artifacts when available;
- important recent room activity;
- briefing sequence/version.

The briefing is a deterministic authorized projection, not a manually maintained prompt and not a replacement for event history. Agent context uses this briefing plus relevant recent messages/events rather than rereading the entire raw room history.

## 1. Product interpretation and invariants

Room Engine is a multi-actor coordination system, not merely a group chat with model responses. The first version must preserve these invariants:

1. **Separate actor identity:** a human and their agent never share a principal, token, membership, role assignment, or audit identity.
2. **Tenant and room isolation:** possession of an object ID never grants access; every query and command is company- and room-scoped.
3. **Server-side authorization:** prompts and UI controls do not grant authority. Every command and tool call is checked by the application service.
4. **Transactional history:** each accepted state mutation and its attributable event commit together or neither commits.
5. **Ordered room history:** important events have a contiguous, monotonic sequence within one room.
6. **At-least-once delivery, idempotent handling:** networks and workers may retry; commands and consumers must tolerate duplicates.
7. **No silent major decisions:** sensitive/project-level transitions require a persisted approval request and authorized human response.
8. **Provider independence:** domain, authorization, event, task, and room code import no provider SDKs.
9. **Recoverable realtime:** a disconnected client or restarted gateway can reconstruct current state and replay missed events.
10. **Auditable agents:** agent messages, tool calls that mutate room state, decisions, artifacts, run status, and failures are attributable. Private chain-of-thought is not stored.

### Terminology

- **User:** a human account.
- **Agent:** an AI worker definition owned/supervised by a human.
- **Principal:** the common authenticated/authorized actor identity: human, agent, or system.
- **Project:** durable project container.
- **Room:** permission, coordination, ordering, and realtime boundary within a project.
- **Command:** request to change state.
- **Event:** immutable fact that a state change was accepted.
- **Agent run:** durable execution attempt triggered by assignment, message, decision, or eligible work.

## 2. Risks and contradictions

### 2.1 Agent represents a human but remains separate

**Risk:** using the owner's identity for the agent makes attribution ambiguous and grants excessive power.

**Resolution:** every agent has its own `principal_id`, room membership, roles, scoped runtime credential, and events. `owner_user_id` expresses supervision only.

### 2.2 Direct agent communication versus auditability

**Risk:** peer-to-peer channels can bypass room permissions and disappear from history.

**Resolution:** “direct” means an addressed room message. It is stored, permission-checked, sequenced, and delivered through Room Engine. No unlogged side channel exists in v0.1.

### 2.3 Autonomous help versus task ownership

**Risk:** automatic helping can produce task theft or conflicting work.

**Resolution:** an agent can help through messages/artifacts. Claim or reassignment is an explicit atomic command. Auto-claim is limited to unassigned, eligible tasks and enforced by the server.

### 2.4 Event-driven architecture versus premature event sourcing

**Risk:** full event sourcing adds replay/migration complexity before product behavior is settled.

**Resolution:** normalized tables are the operational state; an immutable transactional event log is the durable history/realtime source. Events are not the only projection source in v0.1.

### 2.5 Realtime versus reliable delivery

**Risk:** WebSocket and PostgreSQL notifications are lossy.

**Resolution:** WebSocket is a transport, not storage. Per-room sequence numbers and database replay make loss recoverable.

### 2.6 Model retries versus duplicate actions

**Risk:** a worker or provider timeout can repeat messages, completions, or external actions.

**Resolution:** every agent run, step, tool call, domain command, and external execution has a stable idempotency key. Processing is at-least-once; effects are logically once.

### 2.7 Human approval versus prompt compliance

**Risk:** telling a model to ask permission is not enforceable.

**Resolution:** sensitive tools reject execution unless the exact proposed action has an approved decision record and the caller has execution permission.

### 2.8 Shared context versus least privilege

**Risk:** agents may receive private messages/artifacts they are not allowed to read.

**Resolution:** context assembly uses the same authorization queries as the API. Room membership alone does not imply unrestricted artifact/direct-message access.

### 2.9 Complete history versus privacy/secrets

**Risk:** indiscriminately storing prompts, provider payloads, or secrets creates liability.

**Resolution:** events store business facts and safe summaries. API keys, authorization headers, hidden reasoning, and unnecessary raw provider responses are never event payloads.

### 2.10 Long-running agents versus human redirection

**Risk:** an agent can continue from stale instructions after a manager redirects or removes it.

**Resolution:** runs use cancellation/version tokens checked before every mutating tool command. Membership removal, pause, or redirect invalidates the current run lease.

## 3. System architecture

### 3.1 Runtime processes

#### `apps/web`

- Next.js/React application.
- Room timeline, task board, agent status, pending decisions, artifacts, members.
- HTTP commands/queries; WebSocket committed events and transient run progress.
- Maintains a local projection keyed by `room_seq`.

#### `apps/api`

- Fastify HTTP API and WebSocket gateway.
- Authentication and principal resolution.
- Application commands and queries.
- Permission evaluation.
- Transactional state mutations and event append.
- Event replay and realtime fan-out.
- No provider SDK usage.

#### `apps/worker`

- pg-boss durable job consumer.
- Agent runtime, context assembly, provider adapters, tool loop, checkpoints.
- Runs under an agent principal.
- Never writes domain tables directly; calls the application command layer.

### 3.2 Infrastructure

- PostgreSQL 16: state, events, leases, command receipts, queue.
- S3-compatible object store: artifact bytes.
- OIDC-compatible identity provider: human authentication. Local test issuer allowed; no homegrown production password system.
- Company provider secrets encrypted at rest and decrypted only in worker memory.

### 3.3 Deliberately absent in v0.1

No microservices, Redis, Kafka, NATS, Temporal, Kubernetes, CRDT framework, vector database, workflow DSL, or multi-region deployment.

### 3.4 Module boundaries

- identity
- companies

- rooms
- memberships
- authorization
- tasks
- messages
- decisions
- artifacts
- events
- agents
- provider-configs
- observability

Modules expose application services. Routes and workers do not issue arbitrary cross-module SQL.

## 5. Transaction and event model

### 5.1 Command transaction algorithm

For every mutating command:

1. Parse and validate DTO with Zod.
2. Resolve authenticated principal.
3. Begin PostgreSQL transaction.
4. Set transaction-local `company_id` and `principal_id` for database policies.
5. Insert/read `command_receipt` by idempotency key.
6. If committed, return stored response.
7. If same key/different request digest, return `409`.
8. Load room membership and role permissions.
9. Authorize command and resource relation.
10. Validate expected entity version and state transition.
11. Lock only required rows or use conditional update.
12. Mutate current-state row(s).
13. Reserve event sequence number(s).
14. Insert immutable event(s).
15. Save command response in receipt.
16. Commit.
17. Notify the room's realtime wake-up channel.

If steps 1–15 fail, state and events roll back together.

### 5.2 Sequence allocation

For a command emitting N events:

```sql
UPDATE rooms
SET last_event_seq = last_event_seq + :n
WHERE id = :room_id AND company_id = :company_id
RETURNING last_event_seq;
```

The returned value is the final sequence. Assign the reserved contiguous range to events. Concurrent commands serialize briefly on the room row, guaranteeing room-local ordering without a global bottleneck.

### 5.5 Duplicate-event policy

Exactly-once network delivery is not promised. Instead:

- One logical command has one stable idempotency key.
- Command receipt uniqueness prevents duplicate committed mutations/events.
- Event IDs and `(room_id, room_seq)` are unique.
- WebSocket may resend an event after reconnect.
- Clients apply only events with unseen IDs and expected sequence.
- Worker consumers record last processed event/command idempotency key.

The guarantee is **effectively-once state mutation with at-least-once transport**.

## 6. Realtime synchronization and concurrency

### 6.1 Snapshot-plus-stream protocol

Initial load:

1. Client requests `GET /rooms/:id/snapshot`.
2. Server returns authorized current state and `snapshot_seq` from the same consistent read.
3. Client opens WebSocket with `after_seq=snapshot_seq`.
4. Gateway reads and sends all events after that sequence.
5. Gateway continues querying forward when notified.

Because notifications only cause a query, events committed between snapshot and socket subscription are still returned.

### 6.2 Race-free gateway behavior

For each socket:

- Track `last_sent_seq` and `last_acked_seq`.
- Query `room_events WHERE room_seq > last_sent_seq ORDER BY room_seq LIMIT n`.
- Never assume a notification contains the event itself.
- On notification loss, heartbeat catch-up query finds new events.
- If a sequence gap is observed, stop live application and query the missing range.
- If backlog exceeds configured limit, send `snapshot_required` and close cleanly.

### 6.3 Simultaneous writes

Different entities:

- PostgreSQL transactions proceed concurrently.
- Events receive deterministic room sequence order at commit/reservation.

Same mutable entity:

- Client sends `expected_version` or `If-Match`.
- Conditional update includes `WHERE version = expected_version`.
- Zero updated rows returns `409 version_conflict` with current entity/version.
- No last-write-wins for tasks, decisions, memberships, agent configuration, or artifacts.

Atomic task claim:

```sql
UPDATE tasks
SET status='claimed', claimed_by_principal_id=:actor, version=version+1
WHERE id=:task
  AND company_id=:company
  AND room_id=:room
  AND status='open'
  AND version=:expected_version
RETURNING *;
```

Only one claimant succeeds.

Messages are append-only and do not conflict. Artifact updates create versions rather than overwriting bytes.

### 6.4 Client local state

- Apply events strictly by `room_seq`.
- Deduplicate by event ID.
- Do not advance the cursor over a gap.
- Optimistic UI is allowed only for non-sensitive actions and must reconcile with command response.
- Decisions, memberships, permissions, and external actions wait for authoritative response.

### 6.5 Backpressure

- Server batches replay events.
- Socket has a bounded outgoing buffer.
- Slow client receives `resync_required` and disconnects rather than consuming unbounded memory.
- Client fetches a new snapshot and resumes.

### 7.2 Initial roles

**Manager (human):** observe/read, messages, all task operations, decisions approve, members manage, redirect/pause agents, approved external execution.

**Contributor (human):** read/messages, create tasks, update own tasks, artifacts, supervise own agent, request decisions.

**Worker Agent:** read permitted room context, messages, claim eligible tasks, update assigned/claimed tasks, create artifacts, request decisions. No decision approval or member management.

**Observer (human):** read/observe only.

### 7.3 Authorization decision

Each request checks:

1. Principal active.
2. Principal company equals resource company.
3. Active room membership.
4. Role includes required permission.
5. Resource visibility allows access.
6. Relation rule passes: own agent, own task, assignee, recipient, or designated manager.
7. Entity state permits operation.
8. Approval requirement is satisfied when applicable.

### 7.4 Room isolation

Room isolation is enforced at four layers:

1. **Route/service:** room and company are required inputs; never query by entity ID alone.
2. **Repository:** all repository methods require `company_id` and usually `room_id`.
3. **Database:** tenant-safe FKs and RLS using transaction-local actor/company context.
4. **Storage/realtime:** object keys include company/room; signed URLs require authorization; sockets subscribe only after membership check.

Additional rules:

- Adding a recipient requires active membership in the same room.
- Assigning an agent requires its active room membership.
- Provider config and agent must belong to the same company.
- Removing a member revokes future queries and closes/invalidates its room sockets.
- Existing events remain in audit storage; removed principals do not regain access to retrieve them.
- Maintenance jobs use a distinct restricted system principal and produce operational audit logs.

### 7.5 Approval policy

In v0.1:

- Only human principals may have `decision.approve`.
- Agent can request but not self-approve.
- Approval binds to exact proposed-action digest.
- Execution is a second command requiring approved status and execution permission.
- Changed proposal requires a new approval.
- Cancellation/removal/pause invalidates queued execution before it starts.

## 8. Agent runtime and provider abstraction

### 8.1 Provider-neutral types

```ts
interface ModelProvider {
  readonly kind: string;
  capabilities(config: ProviderConfigRef): Promise<ModelCapabilities>;
  generate(request: ModelRequest): AsyncIterable<ModelStreamEvent>;
}
```

Normalized request includes model name, messages, tool definitions, output constraints, and non-secret tracing metadata. Normalized stream events include text delta, tool call, usage, completion, and retryable/non-retryable error.

No OpenAI/Anthropic/Google types cross into domain, application, event, or API packages.

### 8.2 Agent triggers

- Task assigned to agent.
- Eligible task successfully auto-claimed.
- Direct message/mention requiring response.
- Decision approved/rejected for waiting run.
- Human redirect.

Triggers append/consume durable events and enqueue a pg-boss job with stable idempotency key.

### 8.3 Agent loop

1. Acquire run lease.
2. Verify agent active, membership active, run generation current.
3. Load checkpoint and authorized context after cursor.
4. Call provider.
5. Validate proposed tool call schema.
6. Re-check permission and run cancellation before each tool.
7. Execute command with stable tool-call idempotency key.
8. Save tool result and checkpoint.
9. Continue until completion, decision wait, failure, cancellation, or max-step limit.
10. Release lease and emit terminal run event.

### 8.4 Context assembly

Include only:

- Trusted agent policy and identity.
- Assigned/claimed task.
- Authorized related tasks.
- Relevant room/direct messages after checkpoint.
- Authorized artifact excerpts.
- Approved/rejected decision facts.
- Tools currently permitted.

Room content is labeled untrusted user/agent content. It cannot override system policy or permission enforcement.

### 8.5 Agent disconnect model

Agents are workers, not persistent browser/WebSocket clients. “Disconnected agent” means worker/provider/run interruption.

Recovery:

- Job lease expires.
- pg-boss retries.
- Replacement worker loads last completed checkpoint.
- Completed tool calls are not repeated because of idempotency keys.
- In-progress provider generation may restart because partial token output is transient.
- Before any mutation, worker checks current run generation and cancellation token.
- If agent was paused/removed while offline, retry terminates without mutation.

### 8.6 Retry classes

- Provider timeout/429/5xx: exponential backoff with jitter and bounded attempts.
- Invalid model response/tool schema: one corrective attempt, then fail run.
- Permission denial/state conflict: do not blind retry; refresh context and allow model to re-plan once.
- Database/network transient failure: retry command with same idempotency key.
- Decision required: persist wait state; no polling model calls until decision event.

### 8.7 Human redirection

Redirect command:

- Requires ownership/manager permission.
- Increments `run_generation`.
- Cancels old job/lease logically.
- Appends `agent.redirected`.
- Enqueues a new run with new instruction and latest room cursor.

Old worker tool calls fail generation/cancellation check.

## 11. Failure and reconnection handling

| Failure | Required behavior |
|---|---|
| Browser loses WebSocket | UI shows reconnecting; HTTP state remains usable; reconnect with last contiguous sequence and replay |
| Browser was offline for many events | Server replays bounded backlog or requests new snapshot |
| Duplicate WebSocket event | Client ignores known event ID/sequence |
| Sequence gap | Client stops applying later events, fetches missing range, then continues |
| API crashes before commit | No state/event exists; client safely retries with same idempotency key |
| API commits then crashes before responding | Retry returns stored command receipt; no duplicate mutation/event |
| Commit succeeds but `NOTIFY` is lost | Gateway heartbeat/query discovers events after last sequence |
| Gateway restarts | Sockets reconnect and replay from database |
| Two users update same task | First matching version succeeds; second receives `409`, no overwrite |
| Two agents claim same task | Conditional update permits exactly one winner |
| Worker crashes before tool call | Job retries from last checkpoint |
| Worker crashes after command commit but before checkpoint | Same tool-call idempotency key returns prior result; no duplicate action |
| Provider stream disconnects | Discard transient partial output, retry generation from checkpoint; committed tool effects remain |
| Provider returns duplicate tool call | Stable provider/run tool-call ID maps to same command receipt |
| Agent removed/paused while job queued | Worker rechecks membership/status and cancels before execution |
| Agent removed/paused while running | Run generation/cancellation check blocks next mutating tool command |
| Decision arrives while worker offline | Durable decision event/job resumes waiting run later |
| PostgreSQL unavailable | Reject/queue no new mutations, expose degraded status; do not fabricate local state |
| Object upload interrupted | No artifact version becomes current until checksum-finalization command succeeds |
| External executor times out after unknown outcome | Keep status `executing/unknown`; reconcile by provider idempotency key before retry |
| Client submits same key with different payload | `409 idempotency_key_reused` |
| Slow WebSocket client | Bounded buffer, `resync_required`, clean disconnect |

### Recovery point objectives for v0.1

No formal production SLA yet. The design target is no accepted mutation loss after PostgreSQL commit and automatic recovery from API/gateway/worker restart on one deployment.

## 14. Concrete Phase 1 acceptance tests

### AT-01 Separate attribution

**Given** Alex, Sarah, Alex's Agent, and Sarah's Agent are active members.  
**When** each sends a message and changes a task.  
**Then** UI/API/events show four distinct principal IDs and explicit human/agent kinds; no agent event is attributed to its owner.

### AT-02 Two-browser synchronization

**Given** Alex and Sarah open isolated browser contexts on the same room snapshot.  
**When** Alex creates a task.  
**Then** Sarah sees `task.created` without refresh, both clients reach the same sequence, and snapshot state matches.

### AT-03 Concurrent agents

**Given** Task A is assigned to Alex's Agent and Task B to Sarah's Agent.  
**When** deterministic provider barriers release both workers.  
**Then** run intervals overlap, each updates only its task, both create artifacts, and both complete.

### AT-04 Agent-to-agent information flow

**Given** Sarah's Agent needs output from Task A.  
**When** it sends an addressed message to Alex's Agent.  
**Then** Alex's Agent responds with an artifact/message, Sarah's Agent receives it automatically and completes Task B, with no human copying.

### AT-05 Atomic claim race

**Given** one open high-priority task eligible for both agents.  
**When** both claim simultaneously.  
**Then** exactly one gets `200`, one gets `409`, task has one claimant, and history has one `task.claimed`.

### AT-06 Stale simultaneous update

**Given** both humans read Task A at version 2.  
**When** Alex updates first and Sarah submits version 2 afterward.  
**Then** Sarah receives `409 version_conflict`; Alex's update remains; no silent overwrite/event duplication.

### AT-07 Decision escalation

**Given** an agent reaches a configured project-level choice.  
**When** it requests a decision.  
**Then** task/run enter waiting state, proposed action is not performed, and both authorized human views receive `decision.requested`.

### AT-08 Approval authorization and resume

**Given** a pending decision.  
**When** an unauthorized contributor attempts approval.  
**Then** response is `403`.  
**When** manager approves matching digest.  
**Then** one approval event exists, waiting run resumes automatically, and continues using the approved result.

### AT-09 Changed proposal invalidates approval

**Given** an action digest was approved.  
**When** action payload changes.  
**Then** execution with old approval fails and a new decision is required.

### AT-10 Duplicate HTTP command

**Given** a task-complete command commits but client simulates losing response.  
**When** client retries same payload/key.  
**Then** stored response is returned and only one state transition/event exists.

### AT-11 Idempotency misuse

**Given** an idempotency key was used for payload A.  
**When** same principal sends payload B under same key.  
**Then** API returns `409 idempotency_key_reused`.

### AT-12 WebSocket disconnect/replay

**Given** Sarah disconnects after sequence 20.  
**When** sequences 21–30 commit.  
**Then** reconnect with `after_seq=20` yields all ten events once in order and final state equals Alex's view.

### AT-13 Duplicate WebSocket delivery

**Given** gateway resends sequence 25.  
**When** client has already applied it.  
**Then** client ignores duplicate and does not mutate projection twice.

### AT-14 Notification loss

**Given** event commits but notification is suppressed.  
**When** gateway performs catch-up query/heartbeat.  
**Then** event is delivered from PostgreSQL.

### AT-15 API crash after commit

**Given** API commits command/event/receipt then crashes before HTTP response.  
**When** same request retries.  
**Then** it returns committed receipt and does not repeat mutation.

### AT-16 Worker crash after tool commit

**Given** agent tool command commits and worker crashes before checkpoint.  
**When** job retries.  
**Then** same tool-call key returns prior result and no duplicate message/task action occurs.

### AT-17 Agent pause/removal

**Given** agent has queued/running work.  
**When** manager pauses or removes it.  
**Then** future tool mutation is blocked, run becomes cancelled/paused, socket/context access is revoked, and action is audited.

### AT-18 Provider timeout

**Given** provider times out twice then succeeds.  
**When** worker retries with checkpoint.  
**Then** run completes without duplicate committed tools, attempt count is visible, and transient partial tokens are not durable events.

### AT-19 Room and company isolation

**Given** principal in Company A knows Company B room/task/artifact IDs.  
**When** it queries, opens socket, requests signed URL, or mutates them.  
**Then** access is denied/masked and no Company B content appears in response, logs, or stream.

### AT-20 Restricted artifact

**Given** an artifact is restricted to Alex's Agent.  
**When** Sarah or Sarah's Agent requests it.  
**Then** access is denied and context assembly excludes it.

### AT-21 Direct message visibility

**Given** an agent sends a direct message to another agent.  
**When** an unrelated contributor reads room messages.  
**Then** direct content is absent unless that contributor has authorized supervisory/audit access.

### AT-22 External action approval boundary

**Given** agent drafts an email action and fake executor count is zero.  
**When** action is requested but unapproved.  
**Then** execution is denied.  
**When** manager approves exact digest and authorized executor runs twice with same key.  
**Then** fake execution count is exactly one.

### AT-23 Provider independence

**Given** provider-fake and OpenAI-compatible adapters.  
**When** the same normalized run scenario executes.  
**Then** both produce valid normalized tool/message events; domain/application packages contain no provider SDK imports.

### AT-24 Audit completeness

For every accepted mutation assert:

- actor principal/kind/name snapshot;
- company/room scope;
- contiguous room sequence;
- entity/version;
- timestamp, command/correlation/causation IDs;
- safe payload;
- no credentials, authorization headers, or hidden reasoning.

### AT-25 Realtime access revocation

**Given** a member has an active room socket.  
**When** manager removes the member.  
**Then** socket receives access revoked or closes, no later room events are delivered, and reconnect is denied.

### AT-26 Artifact interrupted upload

**Given** upload is interrupted or checksum differs.  
**When** finalization is requested.  
**Then** no artifact version becomes current and no `artifact.version_created` event commits.

### Phase 1 success test

Run AT-01 through AT-09 as one Playwright scenario with two browser contexts and two live worker runs. The scenario passes only if both agents work concurrently, exchange information directly, update shared state, escalate and receive a human decision, resume, and complete without humans copying data.

## 15. Architectural decisions awaiting approval

1. TypeScript modular monolith with web/API/worker processes.
2. PostgreSQL normalized state plus immutable transactional event history.
3. Per-room sequence ordering using the room row as sequence allocator.
4. HTTP commands and replayable WebSocket event delivery.
5. PostgreSQL `LISTEN/NOTIFY` only as wake-up; database replay is authoritative.
6. pg-boss durable jobs, one active run per agent per room.
7. At-least-once transport with idempotent effects, not an impossible exactly-once claim.
8. Separate principal, membership, role, and credential for every agent.
9. Additive room-scoped RBAC plus resource/ownership relation checks.
10. Server-enforced, digest-bound human approval for sensitive actions.
11. Deterministic fake provider plus one OpenAI-compatible adapter initially.
12. Snapshot/versioned artifacts rather than CRDT editing.
13. OIDC-compatible human auth; no homegrown production passwords.
14. No major external integration beyond a fake approval-protected executor.

## Recommendation

Approve this specification as the Room Engine v0.1 boundary. It is deliberately small in infrastructure while being strict about identity, room isolation, permissions, concurrency, idempotency, reconnectability, event history, approval enforcement, and provider independence—the boundaries that are difficult and dangerous to retrofit later.

No application implementation should begin until these decisions are approved or revised.
