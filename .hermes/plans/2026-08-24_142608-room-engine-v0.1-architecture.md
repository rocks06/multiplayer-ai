# Room Engine v0.1 Architecture and Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task only after architecture approval.

**Goal:** Build the smallest production-shaped Room Engine in which two humans and their separately identified AI agents collaborate concurrently in one permissioned project room with durable realtime state, human approvals, and a complete attributable event history.

**Architecture:** A TypeScript modular monolith backed by PostgreSQL, with an API/WebSocket process and a separate agent-worker process sharing one domain/service layer. Domain commands update normalized current-state tables and append an immutable room event in the same database transaction. WebSockets distribute committed events by per-room sequence number; reconnecting clients replay missed events from PostgreSQL.

**Tech Stack:** TypeScript, Node.js, Fastify, PostgreSQL 16, Drizzle ORM, pg-boss, WebSocket, Zod, OpenAPI, Next.js/React, Vitest, Playwright, Docker Compose, S3-compatible artifact storage.

---

## 1. Specification analysis

The product is not primarily a group chat with bots. It is a multi-actor coordination system with five boundaries that must exist from the first version:

1. **Identity:** a human and that human's agent are distinct principals.
2. **Isolation:** every read and command is company- and room-scoped.
3. **Authorization:** agents receive explicit capabilities rather than inheriting all owner privileges.
4. **Coordination:** concurrent work requires claims, versions, idempotency, and deterministic conflict handling.
5. **Auditability:** all accepted state changes must be attributable, ordered, durable, and replayable.

The UI can appear room/conversation-centered, but chat messages alone cannot be the source of project truth. Tasks, decisions, artifacts, memberships, and permissions are first-class records. The event stream connects those records into one chronological room history.

### Recommended product interpretation

- A **Company** owns users, agents, projects, roles, and provider configurations.
- A **User** is a human identity.
- An **Agent** is a separately authorized runtime identity owned/supervised by one user.
- A **Principal** is the common authorization/audit identity for a human, agent, or system process.
- A **Project** is the durable work container.
- A **Room** is the realtime collaboration boundary for a project. v0.1 supports one primary room per project but does not hard-code that invariant.
- A **RoomMember** grants a principal access to a room under one or more roles.
- Commands are accepted only after authentication, room membership, permission, state-transition, and idempotency checks.
- Agent-to-agent communication is “direct” at the product level but still travels through the Room Engine so it remains authorized and auditable.

## 2. Architectural risks and contradictions

| Risk / tension | Why it matters | v0.1 resolution |
|---|---|---|
| Agent represents a human but must remain separate | Reusing the human's token destroys attribution and makes least privilege impossible | Give every agent its own `principal_id`, memberships, roles, permissions, and runtime credential; retain `owner_user_id` only as supervision linkage |
| “Agents communicate directly” versus complete audit history | Peer-to-peer channels can bypass authorization and disappear from history | All agent messages use the room command API; direct messages are addressed events, not an external side channel |
| Automatic helping/priority work can cause task theft | Two agents may claim the same task or override a manager assignment | Atomic `task.claim` transition with eligibility, role match, status, and optimistic-version checks |
| Agents cannot silently make major decisions | Prompt instructions are not enforcement | Sensitive domain transitions and external actions require a server-enforced approval state; model output alone cannot bypass it |
| Event-driven architecture can become premature event sourcing | Rebuilding all current state from events adds complexity and migration risk | Use normalized current-state tables plus an immutable transactional event log; do not use full event sourcing in v0.1 |
| Realtime delivery is not durable delivery | WebSocket packets can be missed or duplicated | Give each room event a monotonic `room_seq`; clients reconnect with `after_seq` and deduplicate by event ID/sequence |
| LLM calls are nondeterministic and retryable | Worker crashes can repeat messages, decisions, or external actions | Persist `agent_run` and step idempotency keys; commands are idempotent; no external action executes directly from model output |
| BYOK secrets can leak into prompts/logs | Provider keys are company secrets | Store only encrypted provider configuration references; redact secrets from events/logs; inject decrypted credentials only inside the worker process |
| Concurrent writes can overwrite newer state | Humans and agents may edit the same task simultaneously | Add integer `version` columns and require expected version for updates; return `409 conflict` with latest state |
| Private/direct data may leak through broad room visibility | Not every participant should read every artifact or message | Resource visibility plus permission checks; v0.1 supports room-visible and explicitly addressed messages/artifacts |
| Prompt injection through messages/artifacts | An agent may treat another actor's content as system authority | Tag all context with provenance; provider prompt separates trusted policy from untrusted room content; tools enforce permissions independently |
| “Complete history” versus deletion/privacy obligations | Immutable logs may conflict with future retention obligations | Store durable event facts, avoid secrets/raw provider payloads, and reserve a future redaction/tombstone policy; do not promise permanent raw-content retention |
| Token streaming can flood the room event log | Thousands of token events add no durable value | Stream transient run progress separately; persist only meaningful messages, tool calls, task transitions, decisions, and run summaries |
| A shared room can become an accidental global workspace | Missing tenant filters are catastrophic | Every tenant-owned row carries `company_id`; service methods require `company_id`; database policies/constraints provide defense in depth |

### Important contradiction to avoid

“Agent may help another agent” does **not** mean it may mutate another agent's task without authorization. In v0.1, help is either:

1. a message or artifact offered to the assignee; or
2. an atomic reassignment/claim explicitly permitted by room policy and task state.

## 3. Smallest technically sound architecture

### 3.1 Deployment units

Use a monorepo with three runtime processes:

1. **Web app (`apps/web`)**
   - Room timeline, task board, decision inbox, artifacts, members, agent status.
   - Uses HTTP for commands/queries and WebSocket for committed room events.

2. **API + realtime gateway (`apps/api`)**
   - Authentication, room authorization, domain commands, queries, event append, WebSocket fan-out.
   - One modular codebase, not microservices.

3. **Agent worker (`apps/worker`)**
   - Claims agent jobs from PostgreSQL through pg-boss.
   - Runs provider adapters and exposes only approved Room Engine tools.
   - Never writes domain tables directly; it calls the same application command layer as a principal of kind `agent`.

Infrastructure for v0.1:

- PostgreSQL: source of truth, job queue, event history.
- S3-compatible object storage: artifact bytes; PostgreSQL stores metadata/checksum.
- No Redis, Kafka, NATS, Temporal, or Kubernetes initially.

### 3.2 Modular monolith boundaries

Keep modules explicit even though deployed together:

- `identity`
- `companies`
- `projects`
- `rooms`
- `membership`
- `authorization`
- `tasks`
- `messages`
- `decisions`
- `artifacts`
- `events`
- `agents`
- `provider-configs`

Modules communicate through application services/domain commands, not ad-hoc cross-table writes.

### 3.3 State and event transaction

For every accepted command:

1. Authenticate principal.
2. Resolve company and room membership.
3. Authorize required permission.
4. Validate domain transition and expected entity version.
5. Check/insert idempotency key.
6. Mutate normalized state.
7. Increment `rooms.last_event_seq` atomically.
8. Insert one or more immutable events with that sequence.
9. Commit.
10. Notify realtime listeners with room ID and newest sequence.

The event table is the durable recovery mechanism. PostgreSQL `LISTEN/NOTIFY` is only a low-latency wake-up signal; if it is lost, clients and gateways recover by reading `events WHERE room_seq > last_seen_seq`.

This preserves reliability without introducing a broker.

### 5.3 Event rules

- Events are immutable; corrections append new events.
- Every state-changing accepted command emits at least one event.
- Rejected/unauthorized commands go to security/application logs, not the collaborative room timeline by default.
- Payloads contain enough data for UI deltas and audit comprehension, but never provider keys or hidden model reasoning.
- Consumers ignore unknown event types/fields and branch on `schema_version`.
- Event order is guaranteed only within one room, which matches the product boundary.

## 6. Realtime synchronization

### 6.1 Contract

- HTTP returns authoritative command result plus `room_seq`.
- WebSocket sends committed events in room-sequence order.
- On connection, client provides its last applied sequence.
- Server backfills missed events from PostgreSQL before switching to live delivery.
- Clients apply events idempotently and track last contiguous sequence.
- If retention or gap limits are exceeded, server sends `snapshot_required`; client fetches a fresh snapshot and resumes from its sequence.

### 6.2 Why not use WebSocket for mutations

Keep commands on HTTP in v0.1 because HTTP gives straightforward authentication, idempotency headers, retry semantics, OpenAPI documentation, and testability. WebSocket is read/notification-oriented except for subscribe, acknowledge, and heartbeat frames.

### 6.3 Multi-instance readiness without overbuilding

PostgreSQL event rows are durable. `LISTEN/NOTIFY` wakes API instances after commits. An API instance that misses a notification queries forward from its last sequence. If traffic later requires a dedicated broker, replace notification fan-out with NATS/Redis without changing the event envelope or client cursor contract.

## 7. Permission model

### 7.1 Authorization order

Every command/query checks:

1. Authenticated principal exists and is active.
2. Principal belongs to the requested company.
3. Principal has active room membership.
4. Principal's role grants the required permission.
5. Resource visibility permits access.
6. Domain-specific relation passes, such as “own task,” owner/supervisor relation, or designated decision approver.

### 7.2 Initial role templates

| Role | Intended principal | Key grants |
|---|---|---|
| Manager | Human | room read/observe, messages, all task operations, decisions approve, member manage, redirect agents |
| Contributor | Human | room read, messages, artifacts, create/update own tasks, supervise own agent |
| Worker Agent | Agent | room read, messages, claim eligible tasks, update own tasks, create artifacts, request decisions |
| Observer | Human | room read/observe only |

The agent does not automatically inherit the owner's manager role.

### 7.3 Approval enforcement

- An agent may create `decision.requested` if it has `decision.request`.
- Only a human principal with `decision.approve` may approve in v0.1.
- Approval is tied to an immutable proposed-action digest/version.
- If the proposed action changes, prior approval is invalid.
- Agent runs waiting for that decision resume from a queued event, not by polling conversational text.
- External execution requires both approved decision state and `external_action.execute`; v0.1 uses a stub executor in tests.

### 7.4 Database defense in depth

Application authorization remains primary. PostgreSQL should also enforce tenant-safe foreign keys and, where practical, row-level policies based on a transaction-local `company_id`/`principal_id`. Do not let the web client connect directly to the database with broad table access.

## 8. Agent interface and provider abstraction

### 8.1 Boundaries

Separate three concepts:

1. **Agent definition:** identity, owner, role, policy, model selection.
2. **Agent runtime:** task/event loop, context assembly, tools, retries, approvals.
3. **Model provider adapter:** translates a neutral generation request into a provider API call.

The room/domain layer knows about agents and agent commands; it does not import OpenAI, Anthropic, or Google SDK types.

### 8.2 Provider interface

```ts
export interface ModelProvider {
  readonly kind: string;
  capabilities(config: ProviderConfigRef): Promise<ModelCapabilities>;
  generate(request: ModelRequest): AsyncIterable<ModelStreamEvent>;
}

export interface ModelRequest {
  model: string;
  messages: NormalizedMessage[];
  tools: NormalizedToolDefinition[];
  responseFormat?: NormalizedResponseFormat;
  temperature?: number;
  maxOutputTokens?: number;
  metadata: {
    companyId: string;
    roomId: string;
    agentId: string;
    runId: string;
  };
}

type ModelStreamEvent =
  | { type: "text_delta"; text: string }
  | { type: "tool_call"; call: NormalizedToolCall }
  | { type: "usage"; usage: NormalizedUsage }
  | { type: "completed"; finishReason: string }
  | { type: "error"; code: string; retryable: boolean };
```

No provider-native response objects escape the adapter package.

### 8.3 Agent runtime interface

```ts
export interface AgentRuntime {
  enqueue(trigger: AgentTrigger): Promise<{ runId: string }>;
  cancel(runId: string, actor: PrincipalContext): Promise<void>;
  resumeFromDecision(decisionId: string): Promise<void>;
}
```

Triggers include task assignment, direct mention, approved decision, and permitted auto-claim wake-up.

### 8.4 Initial Room Engine tools

- `room.send_message`
- `task.get`
- `task.claim`
- `task.update_status`
- `task.complete`
- `artifact.create_text`
- `artifact.get`
- `decision.request`
- `decision.get`
- `task.list_eligible`

Every tool call invokes the command/query service with the agent's principal context. Tool descriptions do not grant authority.

### 8.5 Context policy

An agent receives only:

- its identity and trusted policy;
- room/member information it may read;
- assigned task and related permitted tasks;
- relevant messages/events since its last checkpoint;
- allowed artifact excerpts;
- tool schemas allowed by current permissions.

Do not dump the entire company or room history into every prompt. Context selection is deterministic and permission-aware.

### 8.6 Provider support in v0.1

Implement:

- a deterministic fake provider for tests;
- one OpenAI-compatible adapter for the first real demo;
- adapter contract tests that prevent provider types leaking into runtime/domain packages.

A second production provider can wait, but the interface must make adding it a package-level change rather than a domain rewrite.

## 9. HTTP API and WebSocket contract

Version all routes under `/v1`.

### 9.1 Command conventions

- Bearer/session authentication identifies human principals.
- Agent worker uses short-lived, scoped service credentials mapped to an agent principal.
- Mutating requests require `Idempotency-Key`.
- Versioned updates require `If-Match: <version>` or `expected_version`.
- Responses include `event_id`, `room_seq`, and current entity version.
- `403` means authenticated but unauthorized; `404` may mask inaccessible resources; `409` means state/version conflict.

### Technology choices

- **TypeScript end-to-end:** shared event/API contracts and faster early iteration.
- **Fastify:** explicit server boundary, good schema/OpenAPI/WebSocket support.
- **Drizzle + SQL migrations:** transparent SQL and constraints; avoid hiding authorization-critical queries.
- **PostgreSQL:** state, audit history, locking, sequence allocation, queue.
- **pg-boss:** durable at-least-once worker jobs without adding Redis.
- **Next.js/React:** pragmatic UI for two-browser acceptance testing.
- **Zod:** runtime validation at every network/provider boundary.
- **Vitest + Playwright:** domain/integration and multi-user browser tests.
- **OpenTelemetry-compatible structured logging:** correlation IDs and actor attribution from day one.

## 11. Phase 1 acceptance tests

### A. Identity and attribution

1. Seed one company, manager Alex, contributor Sarah, Alex's Agent, and Sarah's Agent.
2. Open the same room in two isolated browser sessions.
3. Verify each timeline action displays principal name and explicit `Human` or `Agent` badge.
4. Verify an agent event's actor is the agent principal, never its owner.

### B. Room isolation and authorization

1. Create a second company and room.
2. Attempt reads and mutations using principals from the first company.
3. Expect no data leakage and `403/404` responses.
4. Give an observer read access; verify task/message mutations return `403`.
5. Remove a room member; verify its existing WebSocket closes or ceases delivery and future reads fail.

### C. Concurrent agent work

1. Manager creates Task A and assigns Alex's Agent.
2. Manager creates Task B and assigns Sarah's Agent.
3. Deterministic fake providers start both runs behind a barrier.
4. Release both; verify overlapping run intervals.
5. Each agent sends attributable progress, creates an artifact, and completes only its assigned task.
6. Both human browsers converge to identical task state without reload.

### D. Agent-to-agent communication and help

1. Sarah's Agent requests information from Alex's Agent through a direct room message.
2. Alex's Agent responds with an artifact/message after completing Task A.
3. Sarah's Agent receives it automatically and uses it to complete Task B.
4. Verify no human copied content between agents.
5. Verify both messages and artifact access appear in ordered room history.

### E. Atomic task claiming

1. Create one unassigned high-priority task eligible for both agents.
2. Trigger both agents to claim concurrently.
3. Exactly one claim succeeds; the other receives `409 already_claimed` and does not overwrite the assignee.
4. Event history contains exactly one `task.claimed`.

### F. Decision escalation and continuation

1. Agent reaches a configured high-level choice and submits `decision.requested`.
2. Agent run changes to `waiting_for_decision` and does not perform the proposed action.
3. Both humans see the request in realtime.
4. Unauthorized contributor approval returns `403`.
5. Manager approves.
6. An attributable `decision.approved` event is emitted.
7. Waiting agent resumes, incorporates the approved option, and completes its task.

### G. Realtime reconnect and ordering

1. Disconnect Sarah's browser at room sequence N.
2. Produce messages, task updates, and a decision while disconnected.
3. Reconnect with `after_seq=N`.
4. Verify all missed events arrive once in order and final state matches Alex's browser.
5. Repeat one HTTP command with the same idempotency key; verify no duplicate event/entity.

### H. Optimistic concurrency

1. Both humans load Task A at version 2.
2. Alex updates it successfully to version 3.
3. Sarah submits an update expecting version 2.
4. Receive `409 version_conflict` with current version 3; no silent overwrite occurs.

### I. Approval-protected external action

1. Agent drafts an external email action.
2. Stub executor records zero executions before approval.
3. Manager approves the exact action digest.
4. Authorized executor runs once.
5. Retrying the command does not execute twice.
6. Editing the draft invalidates the old approval.

### J. Provider independence

1. Run the concurrency/decision scenario using `provider-fake`.
2. Run one smoke scenario using the OpenAI-compatible adapter and company-supplied test configuration.
3. Assert domain, application, event, and API packages do not import provider SDKs.
4. Provider timeout/retry does not duplicate room commands.

### K. Audit completeness

For every accepted mutation, assert:

- one attributable event exists;
- actor principal and kind are correct;
- company and room IDs are correct;
- room sequence is contiguous;
- timestamp and correlation ID exist;
- no credentials or raw secret values appear in event payload/log output.

## 12. Build now versus deliberately wait

### Must build for Room Engine v0.1

- Company/user/agent/principal separation.
- One project room with membership and role-based permissions.
- Manager, contributor, worker-agent, and observer role templates.
- Tasks with assignment, atomic claim, status transitions, optimistic versions.
- Room and direct messages through the audited engine.
- Decision request, approve/reject, and agent pause/resume workflow.
- Artifact metadata plus basic text/file storage.
- Immutable per-room event log and snapshot/query projections.
- HTTP command API with idempotency.
- Reconnectable WebSocket stream with room sequence cursors.
- Agent worker with deterministic test provider and one real provider adapter.
- Permission-aware context assembly and constrained room tools.
- Two-human/two-agent UI sufficient for the acceptance scenario.
- Structured logs, correlation IDs, secret redaction, and baseline security tests.

### Deliberately wait

- Microservices, Kafka/NATS, Redis, Temporal, Kubernetes, multi-region replication.
- Arbitrary workflow builders or a general policy DSL.
- Explicit-deny/conditional ABAC beyond the initial relation checks.
- Agent marketplaces, public templates, billing, metering invoices.
- Voice/video, mobile apps, presence typing indicators beyond simple online/run state.
- Full document collaboration/CRDT editing. Artifacts are versioned files/text in v0.1.
- Large-scale semantic memory/vector databases. Use task-scoped context and PostgreSQL search initially.
- Autonomous external integrations. Only a stubbed approval-protected executor is needed.
- Multiple production LLM providers beyond the first adapter; preserve the interface and add adapters when demanded.
- Agent-created agents, recursive delegation, cross-company rooms.
- Complex approval quorums, multi-stage approvals, delegation chains.
- Full event-sourced reconstruction of all state.
- Permanent raw prompts, chain-of-thought, or provider payload retention.
- Advanced retention/legal-hold/redaction UI; define policy before production data.

## 14. Architectural decisions requiring approval

1. **Modular monolith, not microservices.** Three processes (web, API, worker), one repository, one PostgreSQL database.
2. **Hybrid state + event log, not full event sourcing.** Normalized tables serve current state; every mutation appends an immutable event transactionally.
3. **HTTP commands + WebSocket events.** WebSocket does not mutate domain state in v0.1.
4. **PostgreSQL sequence/replay + LISTEN/NOTIFY.** No Redis/Kafka initially.
5. **pg-boss for agent jobs.** At-least-once processing plus idempotent domain commands.
6. **Separate principal for every human and agent.** Agent permissions never implicitly equal owner permissions.
7. **Server-enforced approvals.** Agent prompts cannot authorize major decisions or external actions.
8. **TypeScript/Fastify/Next.js/Drizzle.** One language and shared runtime contracts for the first team.
9. **Deterministic fake provider + one OpenAI-compatible production adapter in v0.1.** Other providers wait, but adapter contracts are fixed now.
10. **No CRDT collaborative editing in v0.1.** Shared state consists of events, tasks, decisions, messages, and versioned artifacts.

## Recommendation

Approve this architecture as the Room Engine v0.1 boundary. It is small enough for an early product but protects the boundaries that are expensive to retrofit: distinct actor identity, tenant/room isolation, permission enforcement, idempotent concurrency, durable realtime replay, complete attribution, approval gates, and provider independence.

No major implementation should begin until the ten decisions above are accepted or revised.
